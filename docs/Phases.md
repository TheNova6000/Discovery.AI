## Phase 3 — Single Ground Agent loop [VERIFIED]

- SQLite state store for a single agent's pausable/resumable state.
- **Verify:** run a Ground Agent on one question end-to-end, kill the process mid-run, restart, and confirm it resumes from checkpointed state rather than restarting from scratch. — `scripts/verify_phase3.py`.

## Post-Phase-5 — Epistemic layer (ad hoc research, not a numbered phase; feeds Phase 7)
Not part of the original phase sequence — opened by a design discussion questioning whether synthesis can be trusted just because its inputs were investigated. Fully detailed in Architecture.md §0.2-§0.5 and Memory.md (2026-08-28 entries); summarized here only to keep Phases.md accurate about what exists before Phase 6/7 build on top of it:
- **Structural provenance** (`backend.agents.trace_claim`) — **[VERIFIED]**. Classifies how a resolved question's answer was derived (direct/derived/synthesized/unresolved) from the AgentState tree every run already persists. SQLite-only, no Neo4j.
- **Content provenance** (`backend.questions.audit_synthesis`) — **[VERIFIED, 3 sessions]**. A separate auditor call decomposes a synthesized answer into atomic propositions and classifies each as traceable to the investigated material or not — a traceability judgment, explicitly not a truth judgment. One true-positive detection plus two clean negative controls, including one that specifically ruled out the auditor becoming a truth/consensus detector.
- **Claim relationships** (`backend.questions.analyze_claim_relationships`) — **[PARTIAL, three experiments]**. Six-label taxonomy (complementary/alternative_explanation/contradictory/conditional/sequential/unrelated). Reliably avoids inventing false conflict. Three controlled experiments on one pair (original unparaphrased wording, three different target questions) **confirmed `R = f(claim_a, claim_b, question)`**: the identical pair in identical wording returned `sequential`, then `complementary`, then `alternative_explanation` as only the question changed — including successfully eliciting competing-explanation detection once a question demanded a single primary cause, which two broader "why"/"how" framings did not produce. Real, load-bearing finding for how relationships should eventually be represented (question-relative, not intrinsic to a claim pair) — but still only demonstrated on one claim pair; not yet generalized, and no representation has been designed for where a contextual relationship should live (Architecture.md §0.5).
- None of these three are wired into the default agent/synthesis path — standalone, independently-callable tools only, pending further validation.

- Composes a `Lesson` per concept from its existing `Claim`s, run through `audit_synthesis` before attaching (Rules.md rule 19).
- **Verify:** for a sampled lesson, confirm every sentence traces to a real retrieved `Claim`, the same audit shape `audit_synthesis` already passed 3 real sessions of (Memory.md, post-Phase-5 epistemic layer) — and confirm a concept with zero existing claims correctly produces no lesson rather than a fabricated one.

### Phase 11 — Challenge Engine [VISION]
- Exercise schema (prompt/starter/tests/hidden tests/hints/reference solution) in `/backend/challenges`.
- Docker-backed sandboxed runner (`--network=none`, memory/CPU/wall-time/pids limits).
- Independent validation pipeline: reference solution must pass its own tests; a small set of deliberately broken mutants must each fail at least one test (Rules.md rule 17).
- **Verify (three checks):** (1) a correct reference solution passes; (2) each mutant fails at least one test; (3) a deliberately hostile submission (infinite loop, fork bomb, outbound network call) is contained — times out or is network-refused — without affecting the host process or leaving a container behind.

### Phase 12 — Course/Lesson/Challenge frontend [VISION]
- Portal UI: **path/tree course map** (Architecture.md §0.38.3, not a plain list), lesson view, Monaco-based code editor + "run tests" with a results panel, streak/XP/rank display, pass/module-complete micro-animations reusing `frontend/wasm-fluid`. Plain vanilla JS/HTML/CSS served by the existing FastAPI static mount (Architecture.md §0.38.2/§0.38.3's frontend-approach correction) — no new build step or JS framework.
- Design.md's Learning Portal section filled in properly at this phase (currently provisional defaults, same status the graph-UI section held before Phase 6).
- **Verify (two checks):** (1) a learner can go topic → compiled course → a lesson → a passing exercise, end to end, in the browser; (2) the whole stack — Neo4j, backend, sandbox, frontend — comes up on a single laptop via `docker compose up` + `uvicorn backend.api.app:app` alone, no cloud account, no separate frontend server (PRD.md §9.6.10).

### Phase 13 — Learner Model + gamification + remedial loop [VISION]
- `/backend/learner`: `record_attempt`, `get_mastery`, `next_step` (two consecutive failures on a concept inserts a remedial lesson/exercise before the main path resumes — PRD.md §9.6.7).
- Gamification derivations (Architecture.md §6.3/§0.38.3, Rules.md rule 22): `get_xp`, `get_streak` (with freeze/repair), `get_concept_rank` — all pure reads over the same `record_attempt` log, no separate settable state.
- **Verify (three checks):** (1) simulate a learner failing one concept's exercise twice in a row, confirm `next_step` routes to a remedial insertion rather than the next module, and confirm a learner who passes on the first attempt is not shown any remedial content; (2) confirm XP/streak/rank for a fresh learner with zero attempts are all in an honest "nothing yet" state, never a fabricated starting value; (3) confirm two learners with identical attempt histories always derive identical XP/streak/rank — proof these are pure functions of the log, not path-dependent or mutable independently of it.
