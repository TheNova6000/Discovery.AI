## Phase 3 — Single Ground Agent loop [VERIFIED]

- SQLite state store for a single agent's pausable/resumable state.

## Post-Phase-5 — Epistemic layer (ad hoc research, not a numbered phase; feeds Phase 7)
Not part of the original phase sequence — opened by a design discussion questioning whether synthesis can be trusted just because its inputs were investigated. Fully detailed in Architecture.md §0.2-§0.5 and Memory.md (2026-08-28 entries); summarized here only to keep Phases.md accurate about what exists before Phase 6/7 build on top of it:
- **Structural provenance** (`backend.agents.trace_claim`) — **[VERIFIED]**. Classifies how a resolved question's answer was derived (direct/derived/synthesized/unresolved) from the AgentState tree every run already persists. SQLite-only, no Neo4j.
- **Content provenance** (`backend.questions.audit_synthesis`) — **[VERIFIED, 3 sessions]**. A separate auditor call decomposes a synthesized answer into atomic propositions and classifies each as traceable to the investigated material or not — a traceability judgment, explicitly not a truth judgment. One true-positive detection plus two clean negative controls, including one that specifically ruled out the auditor becoming a truth/consensus detector.
- **Claim relationships** (`backend.questions.analyze_claim_relationships`) — **[PARTIAL, three experiments]**. Six-label taxonomy (complementary/alternative_explanation/contradictory/conditional/sequential/unrelated). Reliably avoids inventing false conflict. Three controlled experiments on one pair (original unparaphrased wording, three different target questions) **confirmed `R = f(claim_a, claim_b, question)`**: the identical pair in identical wording returned `sequential`, then `complementary`, then `alternative_explanation` as only the question changed — including successfully eliciting competing-explanation detection once a question demanded a single primary cause, which two broader "why"/"how" framings did not produce. Real, load-bearing finding for how relationships should eventually be represented (question-relative, not intrinsic to a claim pair) — but still only demonstrated on one claim pair; not yet generalized, and no representation has been designed for where a contextual relationship should live (Architecture.md §0.5).
- None of these three are wired into the default agent/synthesis path — standalone, independently-callable tools only, pending further validation.

#### R4.3 — Parent/subclaim relation fields [BUILT, 2026-09-16]
- **Objective:** implement §0.49's already-specified subclaim relation vocabulary (`SUPPORTED_BY`/`QUALIFIED_BY`/`ILLUSTRATED_BY`/`CONTRADICTED_BY`/`ALTERNATIVE_TO`/`DERIVED_FROM`) as fields directly on `Claim` — no new class (a subclaim IS a `Claim`, per §0.49's own design, confirmed again here, not re-litigated), no new lifecycle enum (this is a separate axis from `ClaimStatus`), no persistence, no automatic status/confidence inheritance.
- **Ten scoping questions answered from the existing design plus new, explicit decisions, not left implicit:**
  1. **Parent vs. subclaim distinction:** none structurally — a claim is a "subclaim" only relative to a specific `parent_claim_id`/`relation_to_parent` pair it carries; the same `Claim` model plays both roles depending on context.
  2. **Cardinality:** one parent per claim, many children per parent — parent/subclaim relations form a **directed forest of claim decomposition** (at most one parent per claim; many independent root claims coexist), not a single tree and not a claim about the shape of the whole Discovery.AI graph (already a network elsewhere in this project, not a tree). Deliberately NOT many-to-many; the current research workflow's own decomposition is already this shape (one question → sequential sub-questions), and a single `parent_claim_id` field is the smallest representation matching it. True multi-parent support would need a separate edge/relation model, not justified here.
  3. **Directional:** yes, always — child → parent, never symmetric.
  4. **Multiple parents:** explicitly not supported in this slice (see cardinality decision above) — a stated scope limitation, not an oversight.
  5. **Both parent and subclaim at once:** yes, and this is the normal, expected shape of nested support (tested: a real 3-level chain).
  6. **Invalid/superseded parent:** no automatic cascading, ever (confidence/status inheritance is explicitly forbidden) — `find_claims_with_invalid_parent` reports (never mutates) a subclaim whose parent is missing or discredited; what to do about it is a later, deliberate orchestration decision, mirroring the "report first, act later" split already established for `assess_claim_validity` → R4.2.

  8. **Domain-only, graph-only, or shared:** domain-only for this slice, matching R4.2's precedent of deferring all persistence questions to R4.4 — no `ClaimNode`/Neo4j schema change.
  9. **Identity and cycle constraints:** a claim cannot be its own parent (model-level validator); `validate_subclaim_graph` (DFS, mirroring R3.2's `validate_task_graph` precedent exactly) rejects an unknown `parent_claim_id` or any parent-chain cycle, direct or indirect.

#### R4.4 — Persistence [BUILT, 2026-09-16 — decision record, then implemented same day]
- **A dedicated decision record (Architecture.md §0.70), not implementation** — per explicit instruction, no code was changed to produce it, mirroring R0/R4.0's own design-before-code precedent. - **Source of truth: Neo4j remains authoritative.** The live `/chat` path, `assess_claim_validity`, and Phase 8.6's artifact all already read `ClaimNode` as the de facto system of record; `backend.reasoning.domain.Claim` is a computation layer that *proposes* graph writes, not a competing store.
